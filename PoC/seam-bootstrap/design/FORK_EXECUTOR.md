## Solution: 5-Phase Execution Model

### Architecture: Two-Layer Execution

```
LinkedFork (Phase 5 output)
      ↓
  ForkExecutor (Phase 5B - this phase)
      ↓ 5-phase coordination
ExecutionContext + MemoryBarrier (Phase 1, 3)
```

## 5-Phase Execution Model

### Phase 1: Setup
```rust
fn phase_setup(&mut self, context: &mut ExecutionContext) -> Result<(), String> {
    for path_state in self.linked.path_states() {
        context.frame_push(256)?;  // Allocate frame in PSSA arena
    }
    self.execution_state.setup_done = true;
    Ok(())
}
```

**Responsibility**: Allocate execution frames
- Each path needs frame for local state
- Allocate in PSSA arena (Phase 1)
- 256 bytes per frame (tunable)

**Integration**: ExecutionContext::frame_push() (Phase 1)

### Phase 2: Dispatch
```rust
fn phase_dispatch(&mut self, _context: &mut ExecutionContext) -> Result<(), String> {
    for path_state in self.linked.path_states() {
        // Placeholder: Sequential execution

```

**Responsibility**: Schedule paths to execution engine
- Current: Sequential placeholder (proof-of-concept)
- Future: Thread pool or async scheduler
- Each path gets independent execution context

**Future Integration**: Phase 5C (Pseudo-code Interpreter)

### Phase 3: Barriers
```rust
fn phase_barriers(&mut self, _context: &mut ExecutionContext) -> Result<(), String> {
    for barrier in self.linked.barriers() {
        barrier.execute();  // Execute memory fence
    }
    self.execution_state.barriers_done = true;
    Ok(())
}
```

**Responsibility**: Execute synchronization barriers
- Calls barrier.execute() for each barrier
- Barriers generated by Phase 3 AutoSync
- Implements RAW/WAR/WAW coordination

**Integration**: MemoryBarrier::execute() (Phase 3)

### Phase 4: Collect
```rust

    // Real implementation would:
    // 1. Wait for all paths to complete
    // 2. Gather status from each path
    // 3. Check for abort conditions (RFP/direct_jump_context)
    // 4. Accumulate results

```

**Responsibility**: Gather results from path execution
- Coordinate with execution scheduler
- Check for abort conditions

**Future Integration**: Phase 6 (Direct Jump) for abort handling

### Phase 5: Join
```rust
fn phase_join(&mut self, _context: &mut ExecutionContext) -> Result<(), String> {
    if self.execution_state.path_results.len() as u32 != self.linked.num_paths() {
        return Err("Join failed: ...".to_string());
    }
    self.execution_state.join_done = true;
    Ok(())
}
```

**Responsibility**: Synchronize paths at join point
- Verify all paths completed
- Check synchronization invariants
- Return to caller only after all paths done

## Design Decisions

### Why 5 Phases?

**Option 1**: Single execute() function
- ❌ Monolithic, hard to test
- ❌ Hard to debug phase failures
- ❌ Can't verify phase ordering

**Option 2**: 5-phase model (chosen)
- ✅ Each phase independently testable
- ✅ Clear responsibility separation
- ✅ Enables monitoring/debugging
- ✅ Follows Linux kernel tasklet model

### Why ExecutionState Struct?

**Option 1**: Boolean per phase
- ❌ Can't verify all_done()
- ❌ Can't accumulate results efficiently

**Option 2**: ExecutionState (chosen)
- ✅ Single verification point
- ✅ Centralized result collection
- ✅ Easier to extend with more state

### Why 256 Byte Frames?

**Option 1**: Fixed size
- ✅ Predictable allocation (current choice)
- ❌ May be too small for complex paths

**Option 2**: Variable size (future)
- Will analyze path complexity
- Determine frame size from compiled metadata

## Architecture Pattern

ForkExecutor follows the **Pipeline Pattern** (common in Linux):

```
┌─────────────┐
│   Setup     │ ← Frame allocation
└──────┬──────┘
       ↓
┌─────────────┐
│  Dispatch   │ ← Path scheduling
└──────┬──────┘
       ↓
┌─────────────┐
│  Barriers   │ ← Synchronization
└──────┬──────┘
       ↓
┌─────────────┐
│   Collect   │ ← Result aggregation
└──────┬──────┘
       ↓
┌─────────────┐
│    Join     │ ← Synchronization point
└─────────────┘
```

Each phase is:
- **Independent**: Can test/debug separately
- **Composable**: Phases build on previous results
- **Verifiable**: ExecutionState tracks progress
